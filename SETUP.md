# Lumen setup and acceptance test

Production: https://lumen-live-arena.fernyeucalyptus8.chatgpt.site

## Hosted deployment

This React + TypeScript app runs on a Cloudflare Worker through Sites. Sites supplies account sign-in, a D1 database, private R2 file storage, and HTTPS. No Supabase credentials are needed. The deployment is private to your account. Sign in with the **same account on both laptops**. Shows, files, pairing codes, and players are scoped to that identity on the server. This version does not include invitations or separate operator roles.

Source is in `lumen/`. `.openai/hosting.json` identifies the existing Site and declares `DB` and `BUCKET`. Keep that project ID on subsequent deployments. `npm run build` type-checks the client and bundles the React application, stylesheet, sample video, and API into `dist/server/index.js`. The hosting package must include `.openai/hosting.json` and `drizzle/` migrations; the Sites source workflow helper performs that packaging and pushes the exact source commit. Publish that package with the Sites private deployment operation. Hosted D1 migrations run before the Worker is published. Do not set `LOCAL_DEV` in production.

## Local development on Windows

Requires Node.js 22 or later and npm. From the `lumen` directory:

```powershell
npm ci
npm run build
npx wrangler d1 migrations apply lumen-local --local
npx wrangler dev --port 8787 --var LOCAL_DEV:true
```

Open `http://localhost:8787`. Wrangler emulates D1 and R2 and persists them in `.wrangler/state`. The `LOCAL_DEV` flag supplies a local test identity only in this local process. It is not an authentication system for a public server. For real cross-network operation, use the HTTPS production deployment and its platform sign-in.

After edits run `npm run build`; Wrangler reloads the built Worker. The initial sample video is bundled, so the app does not depend on a third-party video host during a show. The CC0 flower video comes from [MDN interactive examples](https://interactive-examples.mdn.mozilla.net/media/cc0-videos/flower.mp4). Logo and sponsor SVGs are generated by the app.

## Repeat the two-laptop acceptance test

1. **Laptop A / venue:** connect your LED processor, projector, or TV using HDMI. In the operating system choose **Extend**. Disable sleep and keep the laptop connected to power. Open the production URL and sign in.
2. Open **Venue Player**. Generate a one-time pairing code. The code expires in 10 minutes.
3. In a dashboard signed into the same account, select your saved show (the sample show has a looping video, a logo, and two sponsor choices). Click **Pair a venue player**, enter the code, and connect.
4. On Laptop A click **Open Output**. Allow pop-ups if prompted. Optionally use **Detect screens** and choose the external display. Browser screen permissions vary; the universal fallback is to drag the output window onto the extended display. Click **Go Fullscreen inside that window**. This user gesture also activates playback. Do this before the audience enters. `F` re-enters fullscreen and `Esc` exits it. The output keeps the logical canvas aspect ratio and letterboxes when necessary.
5. Confirm the three sample layers play. The dashboard should say **Online**, show three live layers, and display **Venue confirmed**. The dashboard's program monitor represents desired server state; the status and revision report prove the venue's actual acknowledgement.
6. **Laptop B / remote:** use a genuinely different connection, such as a phone hotspot. Open the same URL, sign in with the same account, and select the same show.
7. Upload a short H.264 MP4 (1080p is the initial target). Drag it into an empty cell on **Background**. Dropping also cues it. The old live video must continue playing. Observe **Downloading**, then **Ready** on the venue status panel. Very small local files can complete too quickly to visibly observe Downloading.
8. Click **Take Live**. Check the physical external screen changes clips without leaving fullscreen. The venue should confirm a new revision and show the new clip as **Live**. Crossfades are adjustable from 0–5000 ms; select Instant cut for zero duration.
9. Disconnect Laptop A's internet without closing its output. Watch the video continue through at least two loops. Laptop B should show **Offline** after about 12 seconds. Dashboard controls remain off the audience screen.
10. Reconnect Laptop A. It fetches the latest desired composition and revision. It does not replay a queue of old play, restart, or take commands. If a newer live revision exists, it loads its assets first and switches once playable. Cued changes alone do not alter the output.
11. Negative test: upload a broken or unsupported MP4, cue it, and wait for an error. The dashboard should explain the failure, Take Live should remain disabled for that cue, and the previous live composition should continue. Cue another valid asset to recover. Failed downloads retry at 15-second intervals while needed.

## Controls and semantics

- The grid is bottom-to-top layer order; the inspector's arrows change the order. Each layer has one cued clip and four saved slots. Click another sponsor in the same row to replace that layer while preserving the background and logo.
- Play/pause, restart, loop, mute, volume, opacity, position, scale, fit/fill, and layer order are **staged in Preview**. Press Take Live to apply them. Preview audio is muted. The output can play audio after its initial local activation, subject to browser permissions.
- **Blackout** immediately updates the desired blackout state and applies at the next player sync (normally within 1.5 seconds), independently of pending asset downloads. Blackout is visual; it does not mute audio. Blackout cannot reach an offline player.
- Show creation and selection are under the show name or folder icon. Media references, clip layouts, transforms, resolution, and live state save to the cloud. Concurrent dashboard writes use version checks; conflicts refresh rather than overwriting a newer edit.
- Uploaded files are limited to 100 MB each: MP4, WebM, PNG, JPEG, WebP, GIF. Uploaded SVG is intentionally excluded. Browser codec support determines whether a file can become Ready. H.264 MP4 offers the broadest practical compatibility. This version downloads whole assets; it does not transcode or stream large movies.
- Output resolution sets logical composition geometry. The browser scales to the connected physical display. Configure the actual HDMI resolution in your OS. 1080p playback must be measured on your target GPU and content.

## How remote control works

Authenticated dashboard requests persist a versioned composition in D1. An authenticated SSE feed streams updated show state and player reports to the dashboard every 1.5 seconds, automatically reconnecting after each bounded stream. The player fetches current desired state and posts its heartbeat and readiness report every 1.5 seconds. No inbound network access, port forwarding, or shared Wi-Fi is required.

Pairing is an owner-bound, atomically consumed, random 8-character code. Server endpoints authorize every show, player, and media operation. Storage keys are random IDs. The venue downloads assets into the Cache API, creates local blob URLs, and validates browser decoding before reporting Ready. On Take Live, the server checks that all online outputs have the cued media Ready. The player keeps the old deck mounted until all new layers load and video playback starts; after the transition it reports the confirmed revision and asset IDs. Audience output errors go into the heartbeat report, never onto the canvas.

The current in-memory composition and blob URLs keep playing through internet loss. Browser cache is best-effort storage: do not clear site data, close the output, reload while offline, or rely on this as unattended signage software. The player must remain open on a powered-on laptop. Browsers may throttle background windows; keep the fullscreen audience window visible. Cache eviction, account session expiry, hardware decoding, and the physical HDMI chain need venue testing.

## Verification

```powershell
npm test
# With the local Wrangler server running:
$env:TEST_URL='http://localhost:8787'
npm test
node scripts/browser-qa.mjs
```

The browser QA script uses installed Microsoft Edge in headless mode on Windows and creates isolated temporary test data and a local browser profile. It exercises real video decoding, fullscreen activation, media upload, readiness, Take Live, offline looping, heartbeat timeout, reconnect, corrupt-video failure, and a mobile viewport. Screenshots go into ignored `qa-output/`. These simulated browser checks do **not** replace the physical two-laptop / two-network / HDMI test above.

## Phased output roadmap

The physical acceptance test is the gate before advanced output work:

1. Output cropping and four-corner projection mapping, with saved calibration and a test pattern.
2. Multiple independently configured outputs, assignment, and health per output.
3. Edge blending with overlap, gamma, and black-level calibration.
4. MIDI mapping, device permissions, and saved controller profiles.

These advanced features are not implemented or advertised as available in this first version.
